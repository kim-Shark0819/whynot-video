# 작업(116 보완 3b): 줄이기 재요청 — dev에서 효과가 없었음, 판정·횟수·로그 보완

`.kiro/steering/quality-week.md`를 따르되 **예산** 절이 우선한다. 116 보완 3(`_shrink_draft`) 위에서 한다.

## 예산 (가장 우선)
- 새 검사는 바뀐 분기만 덮는다. 변형 검사는 바뀐 판정 분기에만 1회 한다.
- 커버리지 측정과 전체 검사 반복은 하지 않는다. `check_vpoc.py` 전체는 마지막에 1번만 돌린다.
- WORKLOG와 리뷰는 각 3~5줄로 쓴다.

## 배경 (dev 실측, 2026-11-03)
Kling O3(상한 2500B)로 초안을 만들었다. 로그는 아래와 같다.
`draft_done bytes=3228 problems=1 shrunk=False ms=145236 format=elements`
- 줄이기 호출은 갔다(시간이 2배). 그런데 결과가 버려졌다.
- 지금 판정은 "상한 안 & 문제 수 안 늘어남" 또는 "문제 수 감소 & 바이트 감소"다.
  - 줄인 결과도 상한을 조금 넘으면 문제 수가 1→1로 같다. 그래서 바이트가 줄어도 버린다.
- 로그에 줄인 결과의 바이트와 문제 수가 없다. 그래서 원인을 알 수 없다.

## 요구사항
1. 판정을 보완한다. 아래 둘 중 하나면 새 결과를 쓴다.
   - (기존) 상한 안이고 문제 수가 늘지 않음
   - (새) **바이트 초과를 뺀 문제 수가 늘지 않고, 바이트가 줄었음**. 상한을 아직 넘어도 더 짧은 쪽을 쓴다.
   - 참고 표시·항목이 빠지는 등 다른 문제가 새로 생기면 지금처럼 버린다.
2. 줄이기를 **최대 2번**까지 한다.
   - 1번째 결과가 아직 상한을 넘고 판정 1을 통과했으면, 그 결과로 1번 더 줄인다.
   - 2번째 목표는 상한의 0.75배다.
   - 각 호출은 원장 key를 다르게 한다(`-shrink`, `-shrink2`).
   - 실패·예외면 그때까지의 가장 좋은 결과로 끝낸다.
3. 줄이기 문구를 보강한다.
   - "지금 N바이트, 상한 M바이트, 최소 K바이트를 줄여야 한다"를 숫자로 준다.
   - 영어 설명의 수식어·반복부터 줄이게 한다.
   - 한국어 대사는 UTF-8에서 한 글자 3바이트라는 점을 알린다. 대사는 바꾸지 않는다.
4. 로그를 더한다.
   - 줄이기 시도마다 `vnew.retake.shrink_try n=<1|2> from=<bytes> to=<bytes> problems=<n> kept=<bool>`을 남긴다.
   - 원문은 남기지 않는다.
5. 상태의 `shrunk`는 한 번이라도 새 결과를 썼으면 true다.
   - 화면 문구는 그대로 둔다.
   - 결과가 아직 상한을 넘으면 기존 problems 문구가 그대로 보인다.

## 검사 (rtk-w 이어서, LLM 가짜)
- 1번째 2700B(초과, 문제 1) → 쓴다 → 2번째 2400B → 쓴다. shrunk=true, 호출 3, 원장 3줄.
- 1번째 2700B → 2번째 예외 → 2700B 결과로 done.
- 1번째 결과에서 참고 표시가 빠짐 → 버린다. 2번째 시도는 없다.
- 1번째가 상한 안 → 2번째 시도는 없다.
- 기존 rtk-w 기대값 중 이번 판정 변경으로 바뀌는 것만 고치고, 이유를 보고에 적는다. 다른 기존 기대값은 바꾸지 않는다.
